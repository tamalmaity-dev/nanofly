# NanoFly v0.3.50 — Live Build Visibility and Deployment Recovery

**Release Date:** 2026-08-30  
**Type:** Reliability, Performance Diagnostics, and Operator UX  
**Urgency:** Recommended

---

## Summary

NanoFly v0.3.50 makes long-running Docker deployments observable and recoverable. Deployment logs now update live in the Project Detail UI, active builds can be cancelled from the log viewer, and the API avoids transferring the complete deployment history on every poll.

The release also fixes stale deployments left behind after a NanoFly restart, prevents updates or reboots from interrupting active builds, adds quiet-build progress messages, and improves build-context diagnostics so operators can distinguish Docker context transfer from application compilation.

This release builds on the cache, concurrency, Compose, naming, and build-safety improvements introduced in v0.3.49.

## Problem Diagnosed

The affected deployment appeared to stop at:

```text
#6 [internal] load build context
```

The investigation showed that the repository clone and Docker context transfer were not the main bottleneck:

- The repository contained 305 files.
- The Docker build context was approximately 74.4 MB in NanoFly's log.
- A completed Docker build transferred approximately 78 MB in 6.7 seconds.
- The main delay was the application's `npm run build` step.
- Next.js compilation took 775.6 seconds, or about 12 minutes 56 seconds, on the two-vCPU deployment server.

The new progress heartbeat and deployment log viewer make this period visible to the operator. The changes do not claim that a CPU-bound application compilation can be made instant; cache reuse, context diagnostics, and better feedback reduce avoidable work and eliminate the appearance of a dead build.

## Added

### 1. NanoFly-style Deployment Log Viewer

The Project Detail deployment tab now uses the dedicated `DeploymentLogsPanel` and provides:

- Deployment history with status, trigger, commit, start time, and duration.
- A selected deployment log viewer with searchable output.
- Live status and log refresh while a deployment is building or deploying.
- Elapsed-time display for active builds.
- Auto-scroll while the operator is at the bottom of the log.
- Preserved scroll position when the operator scrolls up to inspect earlier output.
- Copy and download controls for deployment logs.
- Clear active, success, error, and cancelled states.
- An inline error message when a cancellation request fails.

The existing deployment tab route now renders the reusable panel instead of maintaining a separate inline implementation in `ProjectDetail.tsx`.

### 2. Cancel Build Control

While a deployment is active, the log viewer displays a `Cancel Build` button in both the active-build banner and the selected deployment header.

- Cancellation requires operator confirmation.
- The button is disabled while cancellation is being processed.
- The deployment is marked as cancelled only for the requested deployment.
- The UI refreshes shortly after the cancellation request so the final state is visible.

The previous process-wide `pkill -f 'docker build'` behavior was removed. A global process kill could terminate an unrelated build on the same server; cancellation now uses NanoFly's deployment-owned context cancellation.

### 3. Lightweight Deployment Polling

The deployment list endpoint now supports:

```text
GET /api/services/{serviceID}/deployments?include_logs=0
```

The list response can omit large historical log fields. The UI uses this lightweight response every 1.5 seconds and fetches the full log only for the selected deployment:

```text
GET /api/services/{serviceID}/deployments/{deploymentID}
```

Selected active logs refresh every second. This substantially reduces repeated database reads, JSON payload size, browser work, and API latency when deployment history contains large logs.

The individual deployment endpoint and cancellation endpoint both verify that the deployment belongs to the requested service before returning or mutating it.

### 4. Quiet Build Progress Heartbeats

Long-running commands now emit an informational heartbeat after 15 seconds without output:

```text
[progress] Command is still running; no output for 15s (Docker may be transferring or compiling).
```

Heartbeats are rate-limited to avoid flooding the log. This makes quiet BuildKit context-transfer, dependency-installation, and compiler stages visible without fabricating progress percentages.

### 5. Build Context Diagnostics

Before Docker starts building, NanoFly now records:

- Total context size.
- Number of files.
- The five largest files in the context.

This helps identify oversized PDFs, assets, generated files, or an ineffective `.dockerignore` when BuildKit spends time loading the context.

## Fixed

### 6. Interrupted Deployment Recovery

NanoFly now detects deployment rows left in `building` state after a process restart. On startup it:

- Marks unfinished orphan deployments as `error`.
- Adds an explicit interruption message to their logs.
- Sets an affected service from `deploying` to `error`.
- Allows the operator to redeploy explicitly instead of leaving the service permanently stuck.

### 7. Safe Shutdown During Builds

NanoFly now waits for in-flight deployments during graceful shutdown. If the drain deadline expires, it requests cancellation for deployments owned by the current process and performs a short final wait.

This prevents the process from being killed while the database still reports an active build whenever a graceful shutdown is possible.

### 8. Update and Reboot Protection

System update and reboot operations now check for active unfinished deployments and return a conflict response while builds are running. This avoids terminating Docker builds mid-stream and leaving incomplete deployment records.

Completed deployment records are no longer treated as active merely because their historical status is `building` or `running`; the active check requires `status='building'` and `finished_at IS NULL`.

### 9. Thread-Safe Streaming Logs

The command log writer now safely handles concurrent stdout and stderr writes, flushes complete lines outside its internal lock, and tracks the last output time for heartbeat decisions.

## API Changes

| Endpoint | Change |
|---|---|
| `GET /services/{id}/deployments` | Added optional `include_logs=0` to omit logs from list polling. Existing callers still receive logs by default. |
| `GET /services/{id}/deployments/{deployID}` | Added selected-deployment detail endpoint with full current log and status. |
| `POST /services/{id}/deployments/{deployID}/cancel` | Added service ownership validation before cancellation. |

## Operator Experience

During a deployment, operators can now follow this flow:

1. Open Project Detail → Deployment Logs.
2. Select the active deployment.
3. Watch live status, elapsed time, and streamed output.
4. Use `Cancel Build` if the deployment must be stopped.
5. Review the final status and download or copy the complete log.

A quiet log no longer means that NanoFly has necessarily stopped. The progress heartbeat identifies when Docker or the application compiler is still working.

## Upgrade Notes

- Existing deployment-list clients remain compatible because logs are included unless `include_logs=0` is specified.
- No database migration is required for the new lifecycle recovery behavior.
- A cancelled deployment should be redeployed explicitly after the cause is resolved.
- Application compilation time still depends on the project's framework, dependency graph, cache state, CPU, and memory. The new diagnostics make the true bottleneck visible so application-specific optimizations can be applied safely.
