# NanoFly v0.3.49 — Faster, Safer, and More Reliable Builds and Deployments

**Release Date:** 2026-08-30
**Type:** Performance, Reliability, and UX
**Urgency:** Recommended

---

## Summary

NanoFly v0.3.49 improves the complete application build and deployment path. BuildKit caches are now preserved between deployments, repeated builds can be skipped safely, deployments are serialized per service, Docker resources use stable scoped names, and the Project Detail experience is organized into clearer service-management panels.

The release also adds stronger Compose validation and test coverage, safer build environment handling, explicit build-cache cleanup, and better GitHub webhook deployment metadata.

---

## Performance Improvements

### 1. Preserve BuildKit Caches

- Removed automatic BuildKit cache deletion after successful deployments.
- Weekly automatic cleanup now removes dangling images only and keeps dependency/compiler caches available.
- Added cache mounts for common generated Dockerfiles:
  - npm package cache
  - Python pip cache
  - Go module and compiler caches
  - Next.js `.next/cache`
- Generated Dockerfiles automatically remove cache-mount directives when the host does not support BuildKit, preserving legacy-builder compatibility.

This prevents every deployment from starting dependency installation and application compilation from an empty cache.

### 2. Reliable Build Skip Optimization

- Git commit metadata is captured before `.git` is removed from the build context.
- Same-commit deployments now verify both:
  - the Git commit label; and
  - a build configuration fingerprint.
- The fingerprint includes build settings and build-time environment values.
- Changing build configuration or public build variables correctly forces a rebuild.
- Added `nanofly.build_hash` image labels for traceability.

### 3. Cache-First Base Images

- Docker builds no longer force `--pull` on every deployment.
- Local base images are reused by default for faster builds and fewer registry requests.
- Set `NANOFLY_BUILD_PULL=1` when a fresh base-image check is intentionally required.

### 4. Controlled Build Concurrency

- Deployments for the same service are serialized to prevent duplicate compilers and Docker builds.
- All application, local-folder, Compose, and Nixpacks builds use the global build slot.
- Configure parallel build capacity with `NANOFLY_BUILD_CONCURRENCY`.
- The default is `1`, with accepted values from `1` through `32`.

---

## Security and Reliability Fixes

### 5. Safer Build Environment Injection

- Runtime credentials are no longer automatically passed as Docker build arguments.
- Variables containing passwords, secrets, tokens, private keys, API keys, database URLs, and connection strings are filtered from build arguments.
- Public frontend variables such as `NEXT_PUBLIC_*` remain available during builds.
- `NANOFLY_BUILD_ALL_ENV=1` is available only for legacy projects that explicitly require every environment variable during image creation.

### 6. Stable Service and Image Names

- Added Docker-safe service-name normalization.
- New and renamed services are stored using stable slugs.
- Container names now use safe names and service identifiers.
- Application image tags are scoped to the service ID, preventing same-named services in different projects from overwriting one another.
- Database container lookups use the same naming rules.

### 7. Deployment Cancellation and Webhook Metadata

- Queued deployments can be cancelled cleanly without leaving the service stuck in a deploying state.
- GitHub webhook deployments now preserve commit SHA and commit message metadata.
- Build skip decisions can therefore use the exact webhook commit.

### 8. Explicit Docker Build-Cache Cleanup

- Added `PruneBuildCache` as an explicit Docker-manager operation.
- Added the `build_cache` option to `POST /settings/prune`.
- The Settings UI exposes BuildKit cache cleanup as an opt-in action with a warning that the next deployment will be slower.

## Compose and Deployment Improvements

- Added Compose volume-normalization tests covering named volumes, bind mounts, anonymous volumes, and numeric ports.
- Added Compose-file variant discovery tests for `docker-compose.yml`, `docker-compose.yaml`, `compose.yml`, and `compose.yaml`.
- Added Compose service-label tests to ensure existing labels are preserved while NanoFly management labels are added.
- Improved service-management naming and organization around deployment, storage, healthcheck, server, and advanced settings.
- Added reusable Compose environment, port, volume, and resource parsing helpers for the Project Detail UI.

The service sidebar and settings flow are now closer to a Coolify-style layout:

- General configuration
- Domains
- Environment variables
- Persistent storage
- Advanced settings
- Healthcheck
- Deployment logs
- Runtime logs

The new panel structure keeps service configuration and operational tools easier to find without changing the existing API contract.

## Configuration Reference

| Variable | Default | Purpose |
|---|---:|---|
| `NANOFLY_BUILD_CONCURRENCY` | `1` | Maximum number of concurrent builds |
| `NANOFLY_BUILD_PULL` | disabled | Pull fresh base images when set to `1` |
| `NANOFLY_BUILD_ALL_ENV` | disabled | Legacy escape hatch to inject all environment variables as build arguments |
| `NANOFLY_AUTO_PRUNE` | `1` | Enable weekly dangling-image cleanup |

## Important Deployment Note

The supplied NanoFly deployment log showed Docker context transfer completing in seconds while the Next.js compilation consumed most of the deployment time. v0.3.49 improves the reusable Docker and Next.js caches, but the first clean compilation remains dependent on the application size, Next.js version, dependencies, and available CPU.
